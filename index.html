第 1 章 · 第 1.1 节：屏幕已经亮了，为什么产品还没有开始？

课程位置：第 1 章《从产品构想到工程需求》 · 建议阅读：约 20 分钟（含思考） · 先修知识：能看懂基本 C 函数调用即可 · 实验条件：不需要开发板。
本节要解决的问题：为什么一块能够显示字符串的 SSD1306，并不能自然地发展成一个有三个页面、实时数据和故障提示的产品？

1.1.1 让一块 OLED 显示文字

设想这样一个下午：桌上放着一块 ESP32、一块 128×64 的 SSD1306 OLED，还有一颗 SHT31 温湿度传感器。接好四根线，按照已有代码初始化 I²C，屏幕上出现了 HELLO。你又花了一点时间读出温度，把屏幕上的文字改成 25.6 C。至此，硬件工作正常，驱动也完成了最初的任务。

这一刻的成功是真实的。ESP32 至少已经能够执行程序；I²C 连线、设备地址与初始化顺序在当前条件下能够工作；SSD1306 能接收数据并点亮相应像素。如果我们此时的目的只是验证一块 OLED 是否损坏，实验就可以结束。

可是产品的使用者并不关心 ssd1306_init() 是否返回成功。设想你把这块屏幕装进一个小外壳，摆到办公桌上。使用者希望它持续显示温湿度；按一下旋钮进入历史曲线，转到第三页调整报警阈值；传感器拔掉时不能悄悄把上次的 25.6°C 继续冒充实时温度。重启以后，之前设置的报警阈值最好还在。

从这一刻起，困难发生了变化。最初要解决的问题是如何让像素发光；现在要解决的是用户操作以后，设备应该发生什么变化，以及设备异常时还应保持哪些行为。

这是本书的第一个分界点。我们不会否认底层驱动的重要性，也不会把显示 HELLO 贬低成毫无价值的练习。它是一个明确、必要的验证环节，只是它证明的事情很有限。把一个局部验证当成产品完成，才会让后面的开发陷入迷茫。

1.1.2 第二个需求到来时，原来的代码开始不够用了

最初的程序可能长这样：

/* 示意代码：突出调用关系，不是可编译的完整工程。 */
ssd1306_clear();
ssd1306_draw_string(0, 0, "TEMP");
ssd1306_draw_string(0, 16, "25.6 C");
ssd1306_flush();

它的工作非常直接：准备缓冲区中的像素，把字符画在指定位置，然后发送到屏幕。对于不变的内容，这种写法很合适。但温度每秒都会改变。现在我们必须决定：谁负责每隔一段时间获得新数据？旧字符串如何清除？屏幕正在刷新时，新数据又来了怎么办？

这些问题还没有严重到非得引入 RTOS。我们完全可以先写一个主循环，定期采集温度、重新生成文字、更新屏幕。只要执行时间有界、不会长时间阻塞，这是一种合理的简单实现。

真正的转折发生在新增第二个页面时。按键原先只负责产生“按下”的信息，现在还要决定当前页面是 MONITOR、HISTORY 还是 SETTINGS。当你进入设置页面，旋钮的同一个旋转动作也改变了含义：在主页面，它可能负责切换页面；在编辑状态，它应该修改阈值。与此同时，温度采集仍然要继续，因为用户不看监控页，并不意味着设备可以停止监测。

如果把这一切写进显示驱动，驱动就不得不知道页面数量、报警阈值、按键意义，甚至温度传感器在哪里。这时 ssd1306.c 不再只处理显示硬件，而开始承担整个产品的规则。等你换用另一块屏幕，这些规则又会被迫跟着迁移。

这里可以先停一下，想一个问题：当用户在设置页面调到 30.0°C，真正发生变化的是 SSD1306、当前页面，还是设备的报警配置？ 屏幕上的字符确实会变化，但字符只是结果。报警阈值是设备需要保存和使用的配置，不应由显示驱动拥有。

我们还没有写出新程序，却已经得到了第一个设计依据：“谁负责把信息画出来”和“谁决定信息的含义”需要分开。 这个边界不是为了让文件夹看起来整齐，而是因为它们会由于不同的原因发生改变。

1.1.3 先写出用户经历，而不是先选库

我们把想做的东西称为“三页面桌面环境仪表”。请暂时忽略 ESP32、SSD1306 和 FreeRTOS，站在使用者面前描述设备。

使用者打开仪表，看见当前温度和湿度。旋转编码器后，屏幕切换到历史页，出现最近一段时间的温度趋势。再切到设置页，可以调整高温报警阈值，确认后生效。传感器暂时无法通信时，设备会明确告诉使用者数据不可用，但仍然能够响应页面操作。恢复通信后，新数据重新出现。

这段话是一份产品构想。它给出了体验，却还不能直接用来编程。例如“最近一段时间”究竟是十分钟还是一小时？“暂时无法通信”要等多久才能认定？“能够响应”允许等待多长时间？这些问题会在 1.2 节被改写为可验收的需求。现在，我们先学会识别不同类型的问题。

使用者看到的事情 开发者需要回答的问题 对应的技术方向
监控页的温度不断变化 谁采样、谁保存最新值、何时刷新 定时调度、数据模型、显示刷新
旋钮使页面切换 如何从电平变成一次操作、谁保存当前页 输入事件、消抖、页面状态
历史页显示曲线 怎样保存有限数量的测量样本 环形缓冲区、绘图
设置页可以修改阈值 谁拥有阈值、何时确认、如何防止非法值 配置管理、输入校验
传感器掉线而界面仍可用 失败如何传播，其他功能为何不应被拖住 超时、错误状态、任务或事件调度

这张表不是要你立刻学习表中全部技术。它的用途正相反：让我们知道每项技术究竟为哪一种产品行为服务。当产品只需要两行静态信息时，完整的页面管理框架未必有意义；当产品需要多个页面和用户编辑时，继续在业务代码里到处写像素坐标就会越来越难维护。

技术选择也是可以被产品需求否决的。假设后来希望屏幕上同时显示大量曲线、可滑动菜单与触摸交互，我们就应该重新评估 128×64 单色屏是否合适，而不是因为已经写过 SSD1306 驱动，就坚持让它承担不适合的工作。

1.1.4 三种经常被混在一起的“状态”

要让三页面仪表正常工作，我们至少得分清三类信息。

第一类是测量事实：传感器最近一次报告的温度是多少，这份读数是否有效，何时获得。第二类是设备配置：报警阈值是多少、用户已经确认了什么参数。第三类是界面状态：当前在第几页，设置页是否正处于编辑模式，光标选中哪一项。

例如用户从监控页切到历史页时，变的只有界面状态。温度传感器没有被切换，报警阈值也没有改变。反过来，采集到一条 26.1°C 的新数据时，测量事实变化了，但用户仍然可以停留在设置页。一个设备可以在发生变化后不必立即把全部变化展示给用户，界面也可以改变而不影响设备核心。

为了看清边界，我们可以用三个很小的 C 数据结构表达它们：

/* 概念代码：尚未配齐头文件、存储与调度实现。 */
typedef struct {
    float temperature_c;
    bool valid;
    uint32_t sampled_at_ms;
} measurement_t;

typedef struct {
    float alarm_threshold_c;
} device_settings_t;

typedef enum {
    PAGE_MONITOR,
    PAGE_HISTORY,
    PAGE_SETTINGS
} page_id_t;

这段代码没有一个 SSD1306 函数，也没有 FreeRTOS API。它甚至能在没有硬件的 PC 上存在。原因是我们正在表达产品里需要记住什么，而不是表达怎样从某颗芯片取到它。

你可能会发现，还没有必要把所有信息合并成一个巨大的 global_state_t。我们先辨认信息由谁拥有、谁有权修改、谁只是读取；等到需要跨任务同步时，再讨论怎样安全地传播它们。提前为尚不存在的并发问题设计一套庞大框架，同样会拖慢项目。

现在回看那句“我想显示 25.6°C”。它其实包含两个动作：一处保存 temperature_c = 25.6 的测量事实；另一处根据这个事实产生屏幕内容。显示是对数据的一种呈现，不应该成为数据存在的理由。 以后即便屏幕换成 LVGL，或者网络 API 也需要读取温度，同一份测量事实仍然可以被复用。

1.1.5 沿着一次用户操作，走一遍系统

假设仪表正在监控页，最新有效温度是 25.6°C。用户短按一次编码器上的按键，希望切到历史页。

按键首先只表现为电平变化。机械触点可能在很短时间内抖动，输入模块需要把这些变化识别成一次有效操作。随后，界面控制逻辑收到“切换到下一页”的请求，将当前页从 MONITOR 改成 HISTORY。显示模块再根据新的页面状态与已有历史数据，绘制历史页。

这一过程中，温度采集模块不需要知道用户按了按钮；按键模块不需要知道仪表总共有几个页面；SSD1306 驱动也不需要知道“历史页”这个概念。它们分别承担了一段有边界的工作。

可以把这段执行顺序写成一行简化的流程：

按键电平 → 输入识别 → “下一页”操作 → 当前页更新 → 页面绘制 → OLED 刷新

这不是在要求我们把每个箭头都做成一个 RTOS 任务。它首先是一张责任关系图。一个程序完全可以在同一条线程里依次完成这些操作。等将来引入较慢的采集、通信和多个执行上下文，再决定哪里需要事件队列、互斥锁或任务。

这种划分带来一个立刻可以检验的好处：如果明天我们用 PC 键盘代替编码器，输入模块的实现变了，但“下一页”操作仍然具有相同含义。如果显示换成另一种屏幕，页面规则也没有必要跟着重写。

你从前会调用 draw_string()，但不知道怎样做三页面 UI。现在我们还没写页面渲染函数，却已经能判断：“当前页”属于界面控制模块，不属于 SSD1306 驱动；温度读数属于设备数据，不属于某个页面。 这些判断决定了后面代码应该放在哪个文件里。

1.1.6 故障让架构的价值显现出来

正常情况下，所有方案都可能看起来可用。真正考验设计的，往往是某个设备不再按预期工作。

考虑下面的情景：使用者在历史页浏览数据，SHT31 的接线突然松开。程序下一次读取传感器时得到了 NACK，或者调用一直等到超时。

一种常见实现会不断尝试读取，直到成功为止。假如它在同一个执行上下文里阻塞，而这个上下文又负责处理按钮和屏幕更新，用户就可能发现整个界面也跟着卡住了。更隐蔽的情况是读取已经失败，屏幕却仍在显示上次的 25.6°C；用户不知道那是十秒前的旧值。

我们希望的行为可以先用自然语言描述：读取失败时，测量数据要标记为无效；界面在数据区域显示 --.- 或明确的离线提示；页面操作仍然生效；恢复通信后，新鲜数据可以重新展示。这里的“仍然生效”未来必须有量化的响应时间目标，当前只确定方向。

这个需求至少暗示了三条设计约束。第一，通信等待不能无限延长。 即使继续尝试，也要有受控的超时与重试策略。第二，读数必须携带有效性信息。 数值 0.0°C 和“没有读到温度”是两件事，不能用同一个浮点值代表。第三，采集失败不应直接决定界面停止服务。 系统需要明确把故障影响限制在合适的范围内。

至于具体怎样做到，我们有不止一种选择。一个以固定周期运行、每项操作都能够及时返回的事件循环可以满足需求；使用 FreeRTOS 的独立采集任务和 GUI 任务也可能满足需求。选择哪一个，要等我们知道响应要求、外设耗时、内存预算以及调试成本后再决定。“传感器可能失联”并不能自动推出“必须使用 RTOS”。

在以后的可靠性章节，我们还会把故障区分为不同严重程度。环境仪表的一颗传感器断线通常只意味着相关数据不可用；一台电源控制器的过流则可能要求立即切断输出，必要时由独立硬件保护。用一个统一的错误码表或者软件队列，不能代替硬件安全设计。

1.1.7 设计怎样从需求里长出来

到现在为止，我们已经找到几个职责：采集测量、保存设备信息、接收用户操作、决定当前页面、绘制页面。但不要急着为每个职责建一个文件夹，更不要立即创造 AbstractManagerFactory 一类与问题规模不相称的框架。

先做一个最小设计就够了。应用模型保存温度及有效性、报警阈值等信息；应用控制器接收输入操作并维护当前页面与设置规则；界面渲染器读取这些信息，调用 SSD1306 的绘图能力。传感器服务把测量结果交给应用模型，而不是直接在屏幕上写数字。

一个足够小的结构可能是：

app/
  app_model.h        # 设备数据和界面状态的基本定义
  app_controller.c   # 输入操作引发的状态改变
ui/
  screen_renderer.c  # 根据模型决定画什么
platform/
  fake_sensor.c      # PC 阶段产生模拟测量结果

这里只是帮助理解的候选布局。我们不会在 1.1 节就要求你建立这些文件，也没有规定这些职责必须永远使用四个文件实现。到了第二章，我们会用真正的 CMake 工程检验：接口到底需不需要再拆分，哪些数据不应暴露给其他模块。

假设产品经理突然说：“设置页允许编辑阈值，但只有按下确认键后才生效。”我们便需要区分一个尚未确认的编辑值，以及已经生效的设备设置。这个需求变化会影响设置交互和配置管理，却不应要求 SSD1306 驱动修改 I²C 命令。反过来，换一种字体或显示屏型号，可能影响渲染代码，却不该改变报警条件。

这就是我们判断模块边界的一种实用方法：看看未来哪些需求会让它变化。因不同原因变化的职责，通常不宜长期挤在一起。 这是启发式判断，不是要求一开始拆到最细。对于简单的小工具，适度合并模块可能更清楚。

1.1.8 把“能工作”变成“知道为什么能工作”

本书不会把“实验跑通了”当成唯一验收标准。我们还需要回答：哪些情况被测试过？哪些结论只是合理猜测？如果需求变化，读者能不能独立判断该改哪里？

对于今天的三页面仪表，最早的实验完全可以只在 PC 上进行。我们人为输入一条 25.6°C 的有效测量，观察监控页文字；触发一次“下一页”操作，检查当前页是否改变；再把传感器状态设为无效，检查界面是否显示离线，而不是照常宣称读数有效。

我们还可以故意构造错误。例如在 SETTINGS 页面编辑报警阈值时，向模型注入一条新温度。按我们的职责划分，编辑中的数字不应被新测量覆盖；界面仍应允许保存或取消设置。再比如把当前页切换十次，查看设备阈值是否被意外重置。这些实验暂时不需要逻辑分析仪，但能帮助我们在接真实硬件前发现应用规则中的错误。

把这种检查写成表格，会让后续实现更有方向：

操作或异常 应当观察到的行为 不应发生的行为
新有效温度到来 当前测量值更新 当前页被重置
用户切换页面 显示切到目标页 报警阈值被改变
传感器失联 数值被标记无效、界面仍能操作 永远等待读数或继续冒充实时值
设置页取消编辑 保留已生效阈值 未确认值被写入正式配置

本节这些都是待实现、待验证的行为要求，不是声称已经在 ESP32 实机测得的结果。下一节会将它们进一步写成带编号的需求与测试方案；之后的章节才逐步完成代码和真实硬件验证。

1.1.9 动手之前，先做一次设计判断

请给自己几分钟，不要看代码，完成下面这个小练习。

题目： 三页面仪表新增一种功能：在 MONITOR 页面长按按键两秒，将温度显示单位从摄氏度切换成华氏度。历史数据仍要保存原始测量值，重新启动后保留用户选择的显示单位。

先回答三个问题。第一，按键识别模块应该上报什么样的操作，是否需要知道“摄氏度”和“华氏度”？第二，测量模块内部应该保存摄氏度、华氏度还是两份数值？第三，如果以后 OLED 换成 LVGL，这项功能最理想的情况下需要修改哪些部分？

可以先画一个只有三四个框的草图。不要因为还不会画标准 UML 就停止，也不用急着定义一整套事件总线。只要把谁拥有哪份信息、谁处理什么请求画出来，就已经迈出重要一步。

自查提示（不直接给完整架构）： 按键的物理持续时间属于输入识别问题，单位偏好属于设备配置，单位换算属于数据呈现或明确的格式化策略。试着让任何一个模块都不必同时知道这三件事。想一想：如果为了实现单位切换，你必须修改 ssd1306_send_command()，是不是说明某个职责放错了位置？

如果你能讲清楚上述推理，就已经开始从“调用显示库”走向“组织显示产品”。即使还没有写一行新代码，这种判断依然会影响后面软件能否长期维护。

1.1.10 回到开头：我们到底完成了什么？

开头那块只会显示 25.6 C 的 SSD1306 并没有错。它证明了屏幕与程序的一段路径能够工作。但它没有告诉我们：页面由谁管理、采集失败怎样传播、数据是否新鲜、设置如何确认、用户操作应当影响哪份状态。

这节课做的事情，是把这些被“显示成功”掩盖的问题重新摆到桌面上。我们没有急着选任务数量，也没有先制定一套看起来很完整的类图，而是从使用者能够观察到的行为，逐渐分辨数据、职责和技术选择。

下一节 1.2《让产品构想变成可以验收的需求》 会沿用这个仪表，把“更新要及时”“掉线还可操作”“历史要保存”等模糊描述，转化成带条件、边界与测试方法的需求。之后，我们才有足够的依据决定模块接口、程序结构与执行方式。

本节检查点：如果有人现在提出“再加一个 Wi-Fi 页面”，你不必立刻知道怎么编写 Wi-Fi 代码；但应该先询问它对用户有什么作用、会修改哪类状态、和现有页面如何交互、断网时应出现什么行为。能提出这些问题，就说明你已经开始用产品工程的方法看待技术。

第 1 章 · 第 1.2 节：让产品构想变成可以验收的需求

课程位置：第 1 章《从产品构想到工程需求》 · 建议阅读：约 25 分钟（含纸面推演） · 先修知识：1.1 节中测量事实、设备配置与界面状态的区别 · 实验条件：纸笔或文本编辑器，无需开发板。 本节产出：沿用 REQ-001～REQ-008 的教学需求草案，为每条需求建立正常与边界测试，并把未决选择单独留下。时间、容量和温度范围均为教学假设，待学习者审阅；它们不是用户调研结论，也不是已经测得的硬件能力。

1.2.1 两份看起来都做对了的仪表

上一节，我们把三页面仪表里的测量数据、报警配置和当前页面分开了。现在请设想，把同一句任务交给两位开发者：“显示实时温湿度，可以看历史、改报警阈值，传感器掉线后也能操作。”一周以后，他们各交回一个可以演示的程序。

第一份程序每隔五秒更新屏幕，保存最近六十个温度点。转动旋钮时，报警阈值立即改变；退出设置页也不会撤销。传感器没有新读数时，它继续显示最后一次温度。作者解释说：“保留旧值至少还有参考作用。”第二份程序每秒更新屏幕，保存最近一分钟的数据；阈值要确认才生效，掉线后则把温度换成横线。作者也认为自己完成了任务。

先别急着评价哪位作者写得更好。原来的任务没有规定“实时”是多久，没有说明“最近”按时间还是按点数计算，也没有说旋钮转到的新阈值何时生效。两个人的分歧，有一部分来自任务尚未给出共同的判断依据。即使交换他们使用的编程语言和显示库，这些分歧仍然存在。

这就是本节要跨过的距离：从“我大概知道想要什么”，走到“另一个人能够据此判断某一次行为是否合格”。我们会继续使用同一台桌面环境仪表，把一句模糊承诺逐步写成有条件、有边界、有观察方法的需求。此时不需要会写驱动，也不需要提前学会 RTOS；需要的是愿意追问一句话没有说明的部分。

1.2.2 先把“更新及时”写到能判定

桌面使用者看着 Monitor 页，收到一条新温度以后，希望屏幕及时变化。我们先尝试把“及时”改成“在一秒内”。这似乎已经可测试，但还有两个问题：从什么时候开始计时，看到什么才算结束？

如果从传感器开始转换计时，要求就包括传感器本身的耗时；如果从应用收到有效测量结果计时，要求关注的是应用处理与显示路径。本阶段还没有真实传感器，因此我们采用后一个观察边界：在 Monitor 可见、且样本仍有效的条件下，从应用接收有效样本，到对应的新值在 Monitor 可见，间隔不超过 1000ms。 这就是 REQ-002 的一秒目标，计时起止点也成为约定的一部分。

一条可验收的需求，通常需要说明所处条件、触发输入、预期结果以及允许的时间或数值边界。它不必套用某种固定句式，但不能让测试者重新发明这些信息。“温度变化后刷新”省略了计时起点；“调用刷新函数”只描述一个内部动作，无法保证用户看到了新温度。我们关心的结束点是可见结果。

现在可以写一个足够小的例子：Monitor 已打开，旧值为 25.0°C；在模拟时刻 1000ms，应用收到一条 26.0°C 的有效样本。若新值在 1800ms 可见，耗时是 800ms，满足这个教学目标；若直到 2001ms 才可见，就超出了目标。恰好在 2000ms 可见仍然合格，因为“不超过”包含等号。这里的数字是纸面输入和预期结果，没有程序实际跑出这些日志。

请先想一想：若 26.0°C 的样本到来时用户正在 Settings 页，能否要求屏幕立刻跳回 Monitor 来证明一秒刷新？这样做会打断用户，也与上一节区分页面和测量的目的冲突。REQ-002 约束 Monitor 的新值可见时间，不能单独推出自动跳页。隐藏页面重新打开时的首帧期限，以及连续快速到来的样本是否允许合并显示，需要另行约定，不能从“一秒内”中猜出来。

这也说明，需求不是写得越长越好。我们只补充会影响验收结论的信息；尚未决定的策略则明确留下。眼下的最小成果是一段任何人都能复算的输入与输出，不是一套提前搭好的显示框架。

1.2.3 屏幕上的 25.0°C 还代表现在吗

更新时限有了，但样本停止以后会怎样？假设在 0ms 收到一条有效的 25.0°C，此后再无新数据。到了 5000ms，屏幕仍写着 25.0°C。数字没有算错，却可能传达错误的信息：用户会把一个旧事实理解成当前事实。

一种方案是永远保留最后读数，不作任何标记。它实现简单，也能保留参考值，但使用者无法判断读数年龄。另一种方案是保留旧值，同时清楚显示采样时间和“已过期”；还有一种方案是在当前值区域显示 --.-，明确提示数据不可用。本节沿用 REQ-003 的约束：超过三秒没有更新，就必须明确表示数据过期，不能继续把旧值当作当前有效读数。 保留旧值作为附加参考还是只显示横线，是呈现选择；这两种做法都不能隐藏过期状态。

“三秒”还需要一个边界。本节将过期条件写为 now_ms - last_sample_ms > 3000：距最后一次有效采样恰好 3000ms 时尚未因超时而过期，达到 3001ms 时则应判为过期。纸面推演使用不会倒退的模拟时间，所有样本按顺序输入。真实程序的计时范围、回绕处理和状态检查频率会在后续章节实现；本节不凭一个减法表达式宣称已经解决它们。过期状态到屏幕提示之间允许多少显示延迟，也应在接入实现前补齐。

没有新样本和已经收到明确的失败结果，也要分开理解。前者可能是采集慢了，后者可能是一次读取已经失败。1.1 节要求读取失败时标记数据无效，不能为了凑足三秒而继续显示有效。三秒规则是在缺少更新时防止旧值无限有效的补充条件。它不能证明线缆已经断开，更不能直接诊断出哪颗器件损坏。在本阶段的用户界面中，两者都可以提示“数据不可用”，后续故障章节再细分原因。

由此可以解释为什么不能用 0.0°C 代表错误。零度本身是合法温度；一旦它同时表示“没有测量”，报警判断和历史曲线就会把故障当成真实的低温。保留数值、有效性和采样时刻各自的含义，才有可能区分“测到了零度”“没有测到”和“很久以前测到过”。本节继续使用 1.1 的测量概念，不另造一份不同的数据结构。

1.2.4 故障期间的一次切页，怎样算成功

现在让传感器在用户浏览 History 时失联。屏幕出现“数据不可用”，似乎已经处理了故障；但用户再按下一页，界面两秒以后才变化。离线提示是对的，页面服务却受到了牵连。这个例子把两条需求分开了：数据是否可信，以及数据出问题时用户能否继续操作。

REQ-004 因此采用 200ms 的教学目标。为了能够复测，本节从应用收到一次已经识别好的“下一页”操作开始计时，到目标页面可见结束。这里不包括物理按键的电平采样和消抖时间；那段路径将在输入章节另行计入整机预算。测试者不能在一份报告里从按键触点计时，在另一份报告里从事件处理开始计时，再把结果直接比较。

考虑两种候选设计。第一种在同一个循环里依次做采集和界面处理，只要采集操作能够在分配给它的时间内返回，再加上其他处理和显示耗时，仍可能满足 200ms。它的资源占用少、执行顺序容易跟踪，限制是每个阻塞点都要有明确上限。第二种把采集与界面安排在不同任务里，可以让界面等待采集的机会减少，但会增加任务栈、共享数据和调度分析的工作；如果两者又争用一个被长期占据的资源，拆成任务仍可能卡住。

需求能够排除“无限等到传感器成功才处理输入”的方案，却没有足够证据替我们决定任务数量。后续必须测量各段耗时，证明总响应满足目标。此时把 FreeRTOS 写进需求，只会掩盖尚未完成的分析。

再回看 REQ-001 的“切页不改变测量数据”。它要检查的是切页操作没有重置测量、历史和已生效阈值；它不要求现实中的温度在浏览期间停止变化。纸面测试时可以暂停样本输入，让数据保持不变，专门观察切页的影响。进入真实并发系统后，则要区分数据因正常采集而变化，还是被页面初始化意外清空。

1.2.5 六十个点，为什么不等于一分钟

我们回到第二位开发者的历史页。他保存最近一分钟的数据，第一位保存最近六十个点。如果每秒恰好收到一点，两者看起来相同；一旦采样暂停十秒，或者每两秒才有一个样本，结果就不同了。

REQ-005 选择的是最多保存最近六十个有效采样点，而不是固定一分钟。这个选择让本阶段可以先学习有限容量的数据保留规则，不必同时引入时间窗口重采样。代价也很具体：曲线不能据此标成“最近一分钟”。若真实产品要求固定时间跨度，就需要补充时间轴和缺测段的规则，不能靠修改图注假装已经满足。

纸面上先把样本命名为 S1 到 S61。输入 S1 后，历史只有一个点；输入到 S60 时刚好占满；再输入 S61，预期保留 S2 到 S61，顺序不变。编号用于辨认样本，不是温度值。中间插入一个明确无效的样本，不应把它当成第六十二个有效点，也不应让真实的零度被排除。

设备刚启动、还没有有效样本时，History 应显示“无历史记录”。先画一条好看的固定曲线可以帮助设计版面，却不能作为采集成功的证据。当前 HTML 中的旧 OLED 演示就是页面与状态概念演示：历史曲线为固定示意，设置阈值不能真正提交。阅读时可以用它观察断线后还能切页，但不能拿它验收这八条需求。即使浏览器完全不运行脚本，上面的 S1～S61 推演也足以表达历史保留规则。

1.2.6 旋钮转到了 30.0°C，配置就保存了吗

在 Settings 页中，屏幕显示的数字可能只是一个正在编辑的值。假设原来生效的阈值是 28.0°C，用户转到 30.0°C 后选择取消。若报警逻辑已经在旋转过程中使用 30.0°C，取消操作就没有恢复产品原来的行为。REQ-006 中的“确认才更新”因此要求我们始终分清编辑值和已生效值。

本节采用 0.0～50.0°C、步长 0.5°C 的教学范围。用 28.0°C 开始编辑，增加一次得到 28.5°C，取消后生效值仍是 28.0°C；重新编辑到 28.5°C 并确认，才应更新生效值。测试上下界时，不只看 0.0 和 50.0 能否使用，还要尝试向范围之外调整，检查生效值不会越界。越界操作是停在端点、拒绝并提示，还是采用其他交互，原需求没有冻结，不能把某一个按钮动画当成唯一合格实现。

这里出现了另一个容易混淆的词：“提交”。用户确认编辑，应用接受新阈值，存储器成功持久化，是三个可能分开的时刻。REQ-008 所说的“最近一次成功提交”，需要有能够用于重启恢复的成功证据；仅仅在屏幕上闪出“已保存”不够。

假设 28.0°C 曾经保存成功，用户后来确认 30.0°C，但这一次写入失败。可以选择只有持久化成功才让新值生效，也可以允许 30.0°C 本次运行暂时生效、同时明确提示未保存。前一种方案更容易让运行值和重启值一致；后一种可以继续接受临时设置，却要求界面与测试区分“已生效”和“已持久化”。这份教学需求尚未选择这项失败策略，本节将它列为待决项。 我们不能一边声称需求已经冻结，一边由实现者静默选择。

对已经决定的正常路径，验收仍然很明确：模拟存储确认 28.0°C 保存成功，重启后读回 28.0°C。对损坏配置，至少能检查“不能把未通过完整性检查的内容无条件当作合法配置使用”。默认阈值是多少、是否要求用户重新确认、怎样显示恢复失败，仍需产品决定。记录这些空白，可以阻止开发者把一个随手写的默认值变成无来源的产品承诺。

1.2.7 报警能说“正常”，需要什么证据

当温度达到或超过阈值时报警，听起来已经没有歧义。把生效阈值设为 30.0°C，依次输入 29.5、30.0、30.5°C 三个有效样本，就能检查 REQ-007 的比较边界。等于阈值也要触发；测试里只有明显偏高的 40.0°C，发现不了把“大于等于”错写成“大于”的问题。

接下来，在显示高温之后注入无效样本。如果程序把测量值清零，再用零度参与比较，报警会看起来恢复正常。这种“恢复”没有新的有效温度作为依据。REQ-007 因而还要求无效测量不能被判作正常温度；测试者至少应观察到“测量不可用，不能据此判定正常”的状态。

这不等于本节已经决定了完整的报警状态机。高温报警在数据失效后是否锁存、恢复后如何解除、确认新阈值后何时重新判断、是否需要蜂鸣器和迟滞，都需要进一步的行为选择。我们现在只确定以下边界：有效值达到阈值时应产生高温报警，缺少可信数据不能成为“温度正常”的证据。也不把桌面仪表里的软件提示扩展成真实设备的安全保护承诺。

由这一次故障可以看出，测试既能检查代码，也能发现需求尚未闭合。若测试者不知道应该观察什么，先补充产品决定；若双方已经同意预期结果，程序却表现不同，再定位实现问题。把两者混成一句“测试没过”，会让团队反复修改代码，却始终没有共同目标。

1.2.8 把八条需求和测试接起来

经过前面的推演，我们可以把原有编号整理成一张查阅表。它用于定位具体约束，不代替前文关于计时、失效和未决策略的解释。所有量化数值均为教学假设；这些需求尚未成为经过人工验收的正式产品基线。

1.2.9 亲自走一遍“失去数据，再恢复”的过程

请新建一份纸面或文本记录，列出时刻、输入、测量是否可用、当前页、历史点数、已生效阈值六项。初始阈值取已经成功保存的 30.0°C，历史为空，当前页为 Monitor。这些初始条件也要写下，否则别人无法复现你的推演。

在 0ms 输入一条有效的 25.0°C，给它编号 S1。记录最新样本可用、历史包含 S1，并写下显示最迟应在 1000ms 更新。之后只停止样本输入，不要同时注入明确失败；这样才能单独检查三秒过期规则。在 3000ms 和 3001ms 各记一次判断，后一时刻的数据应被判为过期，历史中的 S1 仍然存在。历史事实与当前读数的有效性不是同一件事。

在 3200ms 输入“下一页”，目标是 History，按 REQ-004 的教学预算，最迟应在 3400ms 可见。再次切到 Settings，把编辑值调整为 31.0°C，然后取消，确认生效阈值仍为 30.0°C。在 4000ms 注入有效样本 S2，温度为 26.0°C，记录数据恢复可用，历史变成 S1、S2，当前页面不因采样而重置。这里没有选择保存失败策略，因为这一轮根本没有提交新配置。

核对时，先找最早发生分歧的一行。如果你在 3000ms 就判为超时，是没有保留严格大于的边界；如果用零度替代过期读数，是混淆了数值与可信性；如果恢复数据时回到 Monitor，是让采集事件额外修改了页面状态。定位到第一处分歧，比只看最后一屏是否漂亮更有用。

这项练习是 CONCEPT 层级的需求推演。当前仓库没有完整应用模拟器或固件测试命令，因此这里不提供虚构的运行命令和日志。以后同一份时间线可以输入带可控时钟的 PC 测试，记录真实断言与耗时；只有执行后才有相应的测试证据。浏览器里的一次鼠标点击，则不能证明真实按键消抖、I²C 超时或整机的 200ms 响应。

1.2.10 换一个条件，独立写出可验收的约定

现在保留这个仪表，只改变一个情境：用户正把阈值从 30.0°C 编辑到 32.0°C，尚未确认，此时收到一条有效的 31.0°C，随后下一次测量失败。请先独立完成，不急着寻找完整代码。

写出你认为应观察到的行为，说明报警判断使用哪一个值、界面是否保留编辑内容，以及用户此时还能做哪些操作。再增加一次“保存失败”的变化，为 1.2.6 中保留的待决策略提出一个有理由的候选决定。它是你的练习提案，不能直接覆盖教材的正式要求。

交给另一位读者的答案至少要有一个明确初始状态、一次正常输入、一次失败输入和各自的预期结果；涉及时间时写清计时起止点；涉及保存时区分编辑、生效和持久化。对方应能按你的描述复算一次正常路径和一次边界路径，而不必追问“这个时候到底算保存了吗”。若答案要求修改 SSD1306 的总线发送函数才能决定保存规则，再回到 1.1 检查职责边界。

自查时可以先确认一件确定的事：未确认的 32.0°C 不能悄悄替代已经生效的 30.0°C，因此有效的 31.0°C 足以触发高温条件。测量失败以后，不能仅因为缺少温度就宣布温度正常。编辑画面是否被报警打断、报警是否锁存、保存失败后使用哪个运行值，则需要你提出一致且可测试的规则；此处不替你选完整方案。

最后，回看开头两份“都做对了”的程序。现在我们能指出某一行为对应哪个 REQ、用哪个 TEST 检查，也能明确说出哪些地方还没有产品决定。能写出编号只是第一步；能解释边界、发现未决项，并在新情境下独立写出测试，才说明需求开始具有工程用途。若仍卡住，请记录具体分歧属于概念、职责设计还是迁移判断，留作学习反馈，不把“看过本节”自动记为已经掌握。

后续第 1 章会继续把这些行为整理为状态与事件；第 2 章再把需要记住的信息和输入输出放进可构建的工程。我们带到下一步的是带着明确空白的需求草案，而非已经通过验证的完整产品规格。
