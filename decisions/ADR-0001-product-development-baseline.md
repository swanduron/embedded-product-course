## 历史讨论原文（保留作设计背景）

# 《现代嵌入式产品工程》五项设计问题答复

以下回答基于此前已经形成的教材设计共识。请严格区分已确认事实、教学工作假设和未确认事项。

**首先明确最高原则：本教材的核心不是完成一台环境监测仪，也不是学习指定的 MCU 和外设，而是通过真实产品开发过程，培养学习者把构想转化为可实现、可验证、可维护、可制造产品的独立工程能力。**

环境监测仪是贯穿教学的载体，它必须具有真实的使用逻辑，但我们不应虚构商业需求来证明某种教学技术的必要性。

## 1. 贯穿产品为谁解决什么问题？

### 已确认的方向

我们选择桌面环境监测仪作为初期贯穿项目，是因为它适合展示一条完整的产品工程链：

产品构想 → 需求定义 → 应用架构 → 外设集成 → 用户交互 → 可靠性验证 → 工程样机 → 产品化。

它不是为了教 SSD1306 而虚构的产品，也不应该因为已经决定使用三页面 OLED，就倒过来编造三个页面的必要性。

### 建议采用的 V1.0 产品定义

**目标用户：** 在家庭、办公室或个人工作台长期使用设备，希望直观了解周围温湿度变化，并在出现需要关注的情况时得到提示的人。

**主要使用环境：** 室内桌面，有相对稳定的供电条件，可进行日常观察和设置，不面向安全关键场合。

**核心用途：**

1. 快速了解当前环境状况。
2. 观察环境参数随时间发生的变化。
3. 当监测指标超出用户设定范围时，明确告知用户。
4. 用户可以查看、理解并调整设备的工作参数。
5. 设备在传感器失联、重启等异常情况下表现可预测。

因此，该产品不是简单的实时数值显示器，也不是以自动环境控制为主要目标的产品。

它首先是一台**具有历史观察、异常提示和可配置交互能力的桌面监测仪**。

是否进一步增加自动控制功能，可以留给后续产品迭代或迁移项目，不应在最初版本中直接引入。

这里有一个特别重要的教学要求：

**三个页面不是先验的产品需求，而是由“查看当前状态、观察历史变化、修改配置”这三个用户任务推导出的候选 UI 方案。**

在正式设计过程中，应允许分析其他交互方案，并说明为什么选择三页面设计。

### 尚未确认

没有真实市场调研数据、用户访谈或商业客户要求。

当前产品定义是具有合理使用情境的教学基线，不得描述为经过市场验证的商业产品需求。

## 2. 技术路线背后有哪些真实约束？

### 已确认的实际条件

- 学习者拥有一批 ESP32-WROOM 裸模块。
- 具备 PCB 设计能力。
- 能够手工焊接 0603 元件。
- 有意设计可更换 MCU 核心板的实验平台。
- 认可 ESP32 作为主要实验平台，并希望在后续使用 RP2040 验证移植性和低成本方案。
- 愿意购买适当的实验器件，采购成本不是当前主要障碍。
- 希望使用 PC 仿真和自动化测试减少完全依赖实物调试的情况。
- 当前教材项目已经放入本地 Git 工作目录，并使用 GitHub 同步。

### 已确认的教学技术方向

- C 语言、工程模块化、CMake 和 Git。
- GPIO、I²C、SPI、中断、DMA 等基础机制。
- 事件驱动、状态机、按键消抖及输入服务。
- FreeRTOS 任务调度和任务间通信。
- 统一故障管理与系统可靠性。
- SSD1306 显示，以及从基础绘图发展到完整 UI 架构。
- LVGL，用于学习更复杂的图形交互。
- ESP32、RP2040 和 PC 环境之间的可移植架构。
- 从开发板原型收敛到专用硬件。

### 必须避免的误解

**教学路线中包含某个技术，不代表产品必须使用该技术。**

例如：

- 简单三页面 OLED 不一定需要 LVGL。
- 简单周期采集不一定需要 FreeRTOS。
- 单个 I²C 设备不一定需要总线多路复用器。
- 选择 ESP32 不意味着 RP2040 无法满足最终产品需求。

教材必须分析这些技术的适用条件和代价。

可更换 MCU 实验板的角色是**产品构想验证平台和教学实验平台**。其丰富的外设不能直接等同于最终产品所需的硬件。

### 尚未确认的条件

目前没有确定以下硬性限制：

- 项目总预算上限。
- 最终单机 BOM 成本目标。
- 固定采购渠道。
- 所有器件的实际库存。
- 最终产品尺寸、功耗及外壳规格。
- 最终产品 MCU 型号。
- 必须使用的 PCB 生产厂商。
- 商业化目标和销售地区。

请不要自行补全这些条件。课程确实需要这些约束时，应将其明确标注为教学假设或待确认项目。

## 3. 需求分析应在多大程度上依据真实使用情况？

**同意采用你建议的第二种方式：先建立有理由、可追溯的教学假设，再在指定工程阶段进行验证和修订。**

但这不意味着可以随意选择技术指标。

每个需求都应该说明：

1. 对应什么用户任务或系统风险。
2. 为什么需要这个指标。
3. 当前是否具有实际证据。
4. 如果指标不合适，影响哪些设计决策。
5. 计划在哪个阶段重新验证。

建议将需求明确分为以下状态：

- `CONFIRMED`：已经由课程设计者确认。
- `ASSUMED`：为了教学推进而暂时采用。
- `VALIDATED`：已经通过指定测试取得支持证据。
- `REJECTED`：验证后不再采用。
- `OPEN`：尚待分析或决定。

注意，确认需求与验证需求是两种不同的事情。一个已确认的需求仍可能尚未通过实测。

例如：

**每秒采样一次：** 可以作为初期教学假设，但要说明它适用于什么样的环境变化，而不是因为程序容易实现。

**三秒判定数据过期：** 必须分析采样周期、通信超时、容错策略和使用体验，不能直接变成普遍规则。

**保存六十个历史点：** 需要说明采样间隔和历史观察窗口。六十个连续秒级数据点只代表一分钟历史，并不一定能满足用户观察环境长期变化的需求。

教材应适时引入降采样、历史窗口、存储容量和数据完整性等设计问题。

### 教学节奏建议

在第一章形成产品需求假设。

在 PC 原型阶段验证交互和软件行为。

在实际 MCU 集成阶段验证时间、资源与通信限制。

在工程样机阶段重新审查产品指标。

在产品化阶段通过实测确定最终验收要求。

**需求假设应成为教学内容的一部分，而不是被隐藏的简化条件。**

## 4. 工程样机和小批量验证要做到什么程度？

### 已确认的方向

此前已经决定，课程不能在“原型机能够运行”时结束。

整个课程必须覆盖：

**P0：功能原型**

证明核心功能能够实现，允许使用通用开发板、实验底板、仿真环境和临时代码。

**P1：工程样机**

完成相对清晰的软硬件架构，支持故障处理、可重复构建、测试、版本管理，并向专用产品硬件收敛。

**P2：小批量验证**

关注装配一致性、生产测试、烧录流程、运行可靠性、器件可获得性、BOM 和维护机制。

### 我建议采用的实际教学目标

P0 必须实现。

P1 应以实际制造、焊接并验证至少一台工程样机为目标，而不只是绘制 PCB。

P2 建议以三至五台设备作为小批量一致性验证的初步教学规模，但这只是建议值，尚未获得课程设计者正式确认。

在 P2 阶段，教材应指导学习者完成：

- 可重复的固件构建和烧录流程。
- 板级功能测试。
- 设备配置和版本识别。
- 故障注入及恢复验证。
- 持续运行测试。
- 装配及生产测试记录。
- BOM、硬件版本和固件版本的对应关系。

### 必须区分教学目标与实际成果

如果某个阶段只完成了 PCB 设计、BOM 或产测方案，那么只能标记为**设计完成**。

如果只有一台实物，就不能宣称已经验证小批量一致性。

如果未执行持续运行测试，就不能标记为长期稳定性已验证。

如果缺乏实际硬件验证，Agent 不得通过模拟运行结果代替实测证据。

具体测试时长、样机数量、预算和可制造性要求应在相应章节制定时继续细化。

当前不应擅自把上述建议门槛写成已经确认的硬性条件。

商业化认证、市场准入及具体法规符合性，也不能仅凭教学项目的完成情况宣称已经满足。

## 5. 正文如何进入“已审核”状态？

建议正式采用多维度审核制度，而不是用单个 `approved` 字段表示一切完成。

### 编辑自审

由写作 Agent 完成。

主要检查：

- 章节是否真正围绕产品问题展开。
- 是否有完整、连贯的教材叙事。
- 是否说明技术选择的原因与代价。
- 是否逐步推导，而不是罗列知识点。
- 是否存在空泛结论、无解释代码或 AI 风格提纲。
- 是否正确衔接前置章节。

### 技术审核

由独立审查 Agent 或指定审查人执行，结合自动化工具和可复现证据。

主要检查：

- 技术论述是否准确。
- 代码是否能够在声明的环境中构建。
- 测试结果是否真实可复现。
- 硬件实验是否明确区分仿真和实测。
- 是否违反既有架构接口及课程决策。

Agent 自己声称“已经验证”不能代替实际验证记录。

### 学习反馈

由实际学习者提供。

尤其应检查：

- 能否理解问题是怎样产生的。
- 能否解释设计决策。
- 能否独立修改案例。
- 能否把方法迁移到一个新需求。

只看完正文、回答选择题或复制运行示例代码，都不能自动证明已经掌握。

### 最终批准

**由课程负责人，即用户本人，决定章节是否正式批准。**

写作 Agent、审查 Agent 可以提出建议，但不能自行授予最终发布批准。

学习效果也应由实际完成的练习和学习者反馈记录，不由 Agent 主观宣布。

### 建议的状态管理

每一节分别记录：

- 写作状态。
- 编辑审核状态。
- 技术验证状态。
- 学习反馈状态。
- 发布批准状态。

允许未批准内容进入预览环境，但必须清楚标记为草稿或待审核版本。

**正式发布、技术验证、学习者掌握是不同维度，不应混淆。**

# 最后补充一条重要要求

这五项问题的处理方式，也应该体现本教材的根本理念：

**当真实信息不足时，建立明确假设并推进可验证的工程设计，而不是停下来等待所有条件完美，也不是把假设偷偷包装成事实。**

我们的教学目标不是一次性设计出唯一正确的产品。

而是通过需求提出、假设建立、方案比较、原型实现、测试验证和设计修订，让学习者逐渐建立独立的工程判断能力。

请将以上内容作为课程设计讨论的正式答复。

已经确认的原则可以进入治理规范；建议性的产品参数、制作数量及验收门槛，应保留其假设状态。

**不要因为这些回答而再次将教材重构为外设技术清单。产品开发过程始终是主线，具体技术始终服务于产品需求。**
