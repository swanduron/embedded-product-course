# 第 1 章 · 第 1.1 节：屏幕已经亮了，为什么产品还没有开始？

> **课程位置**：第 1 章《从产品构想到工程需求》 · **建议阅读**：约 20 分钟（含思考） · **先修知识**：能看懂基本 C 函数调用即可 · **实验条件**：不需要开发板。  
> **本节要解决的问题**：为什么一块能够显示字符串的 SSD1306，并不能自然地发展成一个有三个页面、实时数据和故障提示的产品？

## 1.1.1 让一块 OLED 显示文字

设想这样一个下午：桌上放着一块 ESP32、一块 128×64 的 SSD1306 OLED，还有一颗 SHT31 温湿度传感器。接好四根线，按照已有代码初始化 I²C，屏幕上出现了 **HELLO**。你又花了一点时间读出温度，把屏幕上的文字改成 `25.6 C`。至此，硬件工作正常，驱动也完成了最初的任务。

这一刻的成功是真实的。ESP32 至少已经能够执行程序；I²C 连线、设备地址与初始化顺序在当前条件下能够工作；SSD1306 能接收数据并点亮相应像素。如果我们此时的目的只是验证一块 OLED 是否损坏，实验就可以结束。

可是产品的使用者并不关心 `ssd1306_init()` 是否返回成功。设想你把这块屏幕装进一个小外壳，摆到办公桌上。使用者希望它持续显示温湿度；按一下旋钮进入历史曲线，转到第三页调整报警阈值；传感器拔掉时不能悄悄把上次的 25.6°C 继续冒充实时温度。重启以后，之前设置的报警阈值最好还在。

从这一刻起，困难发生了变化。最初要解决的问题是**如何让像素发光**；现在要解决的是**用户操作以后，设备应该发生什么变化，以及设备异常时还应保持哪些行为**。

这是本书的第一个分界点。我们不会否认底层驱动的重要性，也不会把显示 `HELLO` 贬低成毫无价值的练习。它是一个明确、必要的验证环节，只是它证明的事情很有限。把一个局部验证当成产品完成，才会让后面的开发陷入迷茫。

## 1.1.2 第二个需求到来时，原来的代码开始不够用了

最初的程序可能长这样：

```c
/* 示意代码：突出调用关系，不是可编译的完整工程。 */
ssd1306_clear();
ssd1306_draw_string(0, 0, "TEMP");
ssd1306_draw_string(0, 16, "25.6 C");
ssd1306_flush();
```

它的工作非常直接：准备缓冲区中的像素，把字符画在指定位置，然后发送到屏幕。对于不变的内容，这种写法很合适。但温度每秒都会改变。现在我们必须决定：谁负责每隔一段时间获得新数据？旧字符串如何清除？屏幕正在刷新时，新数据又来了怎么办？

这些问题还没有严重到非得引入 RTOS。我们完全可以先写一个主循环，定期采集温度、重新生成文字、更新屏幕。只要执行时间有界、不会长时间阻塞，这是一种合理的简单实现。

真正的转折发生在新增第二个页面时。按键原先只负责产生“按下”的信息，现在还要决定当前页面是 `MONITOR`、`HISTORY` 还是 `SETTINGS`。当你进入设置页面，旋钮的同一个旋转动作也改变了含义：在主页面，它可能负责切换页面；在编辑状态，它应该修改阈值。与此同时，温度采集仍然要继续，因为用户不看监控页，并不意味着设备可以停止监测。

如果把这一切写进显示驱动，驱动就不得不知道页面数量、报警阈值、按键意义，甚至温度传感器在哪里。这时 `ssd1306.c` 不再只处理显示硬件，而开始承担整个产品的规则。等你换用另一块屏幕，这些规则又会被迫跟着迁移。

这里可以先停一下，想一个问题：**当用户在设置页面调到 30.0°C，真正发生变化的是 SSD1306、当前页面，还是设备的报警配置？** 屏幕上的字符确实会变化，但字符只是结果。报警阈值是设备需要保存和使用的配置，不应由显示驱动拥有。

我们还没有写出新程序，却已经得到了第一个设计依据：**“谁负责把信息画出来”和“谁决定信息的含义”需要分开。** 这个边界不是为了让文件夹看起来整齐，而是因为它们会由于不同的原因发生改变。

## 1.1.3 先写出用户经历，而不是先选库

我们把想做的东西称为“三页面桌面环境仪表”。请暂时忽略 ESP32、SSD1306 和 FreeRTOS，站在使用者面前描述设备。

使用者打开仪表，看见当前温度和湿度。旋转编码器后，屏幕切换到历史页，出现最近一段时间的温度趋势。再切到设置页，可以调整高温报警阈值，确认后生效。传感器暂时无法通信时，设备会明确告诉使用者数据不可用，但仍然能够响应页面操作。恢复通信后，新数据重新出现。

这段话是一份**产品构想**。它给出了体验，却还不能直接用来编程。例如“最近一段时间”究竟是十分钟还是一小时？“暂时无法通信”要等多久才能认定？“能够响应”允许等待多长时间？这些问题会在 1.2 节被改写为可验收的需求。现在，我们先学会识别不同类型的问题。

| 使用者看到的事情 | 开发者需要回答的问题 | 对应的技术方向 |
|---|---|---|
| 监控页的温度不断变化 | 谁采样、谁保存最新值、何时刷新 | 定时调度、数据模型、显示刷新 |
| 旋钮使页面切换 | 如何从电平变成一次操作、谁保存当前页 | 输入事件、消抖、页面状态 |
| 历史页显示曲线 | 怎样保存有限数量的测量样本 | 环形缓冲区、绘图 |
| 设置页可以修改阈值 | 谁拥有阈值、何时确认、如何防止非法值 | 配置管理、输入校验 |
| 传感器掉线而界面仍可用 | 失败如何传播，其他功能为何不应被拖住 | 超时、错误状态、任务或事件调度 |

这张表不是要你立刻学习表中全部技术。它的用途正相反：让我们知道**每项技术究竟为哪一种产品行为服务**。当产品只需要两行静态信息时，完整的页面管理框架未必有意义；当产品需要多个页面和用户编辑时，继续在业务代码里到处写像素坐标就会越来越难维护。

技术选择也是可以被产品需求否决的。假设后来希望屏幕上同时显示大量曲线、可滑动菜单与触摸交互，我们就应该重新评估 128×64 单色屏是否合适，而不是因为已经写过 SSD1306 驱动，就坚持让它承担不适合的工作。

## 1.1.4 三种经常被混在一起的“状态”

要让三页面仪表正常工作，我们至少得分清三类信息。

第一类是**测量事实**：传感器最近一次报告的温度是多少，这份读数是否有效，何时获得。第二类是**设备配置**：报警阈值是多少、用户已经确认了什么参数。第三类是**界面状态**：当前在第几页，设置页是否正处于编辑模式，光标选中哪一项。

例如用户从监控页切到历史页时，变的只有界面状态。温度传感器没有被切换，报警阈值也没有改变。反过来，采集到一条 26.1°C 的新数据时，测量事实变化了，但用户仍然可以停留在设置页。一个设备可以在发生变化后不必立即把全部变化展示给用户，界面也可以改变而不影响设备核心。

为了看清边界，我们可以用三个很小的 C 数据结构表达它们：

```c
/* 概念代码：尚未配齐头文件、存储与调度实现。 */
typedef struct {
    float temperature_c;
    bool valid;
    uint32_t sampled_at_ms;
} measurement_t;

typedef struct {
    float alarm_threshold_c;
} device_settings_t;

typedef enum {
    PAGE_MONITOR,
    PAGE_HISTORY,
    PAGE_SETTINGS
} page_id_t;
```

这段代码没有一个 SSD1306 函数，也没有 FreeRTOS API。它甚至能在没有硬件的 PC 上存在。原因是我们正在表达产品里**需要记住什么**，而不是表达**怎样从某颗芯片取到它**。

你可能会发现，还没有必要把所有信息合并成一个巨大的 `global_state_t`。我们先辨认信息由谁拥有、谁有权修改、谁只是读取；等到需要跨任务同步时，再讨论怎样安全地传播它们。提前为尚不存在的并发问题设计一套庞大框架，同样会拖慢项目。

现在回看那句“我想显示 25.6°C”。它其实包含两个动作：一处保存 `temperature_c = 25.6` 的测量事实；另一处根据这个事实产生屏幕内容。**显示是对数据的一种呈现，不应该成为数据存在的理由。** 以后即便屏幕换成 LVGL，或者网络 API 也需要读取温度，同一份测量事实仍然可以被复用。

## 1.1.5 沿着一次用户操作，走一遍系统

假设仪表正在监控页，最新有效温度是 25.6°C。用户短按一次编码器上的按键，希望切到历史页。

按键首先只表现为电平变化。机械触点可能在很短时间内抖动，输入模块需要把这些变化识别成一次有效操作。随后，界面控制逻辑收到“切换到下一页”的请求，将当前页从 `MONITOR` 改成 `HISTORY`。显示模块再根据新的页面状态与已有历史数据，绘制历史页。

这一过程中，温度采集模块不需要知道用户按了按钮；按键模块不需要知道仪表总共有几个页面；SSD1306 驱动也不需要知道“历史页”这个概念。它们分别承担了一段有边界的工作。

可以把这段执行顺序写成一行简化的流程：

```text
按键电平 → 输入识别 → “下一页”操作 → 当前页更新 → 页面绘制 → OLED 刷新
```

这不是在要求我们把每个箭头都做成一个 RTOS 任务。它首先是一张**责任关系图**。一个程序完全可以在同一条线程里依次完成这些操作。等将来引入较慢的采集、通信和多个执行上下文，再决定哪里需要事件队列、互斥锁或任务。

这种划分带来一个立刻可以检验的好处：如果明天我们用 PC 键盘代替编码器，输入模块的实现变了，但“下一页”操作仍然具有相同含义。如果显示换成另一种屏幕，页面规则也没有必要跟着重写。

你从前会调用 `draw_string()`，但不知道怎样做三页面 UI。现在我们还没写页面渲染函数，却已经能判断：**“当前页”属于界面控制模块，不属于 SSD1306 驱动；温度读数属于设备数据，不属于某个页面。** 这些判断决定了后面代码应该放在哪个文件里。

## 1.1.6 故障让架构的价值显现出来

正常情况下，所有方案都可能看起来可用。真正考验设计的，往往是某个设备不再按预期工作。

考虑下面的情景：使用者在历史页浏览数据，SHT31 的接线突然松开。程序下一次读取传感器时得到了 NACK，或者调用一直等到超时。

一种常见实现会不断尝试读取，直到成功为止。假如它在同一个执行上下文里阻塞，而这个上下文又负责处理按钮和屏幕更新，用户就可能发现整个界面也跟着卡住了。更隐蔽的情况是读取已经失败，屏幕却仍在显示上次的 25.6°C；用户不知道那是十秒前的旧值。

我们希望的行为可以先用自然语言描述：读取失败时，测量数据要标记为无效；界面在数据区域显示 `--.-` 或明确的离线提示；页面操作仍然生效；恢复通信后，新鲜数据可以重新展示。这里的“仍然生效”未来必须有量化的响应时间目标，当前只确定方向。

这个需求至少暗示了三条设计约束。**第一，通信等待不能无限延长。** 即使继续尝试，也要有受控的超时与重试策略。**第二，读数必须携带有效性信息。** 数值 `0.0°C` 和“没有读到温度”是两件事，不能用同一个浮点值代表。**第三，采集失败不应直接决定界面停止服务。** 系统需要明确把故障影响限制在合适的范围内。

至于具体怎样做到，我们有不止一种选择。一个以固定周期运行、每项操作都能够及时返回的事件循环可以满足需求；使用 FreeRTOS 的独立采集任务和 GUI 任务也可能满足需求。选择哪一个，要等我们知道响应要求、外设耗时、内存预算以及调试成本后再决定。**“传感器可能失联”并不能自动推出“必须使用 RTOS”。**

在以后的可靠性章节，我们还会把故障区分为不同严重程度。环境仪表的一颗传感器断线通常只意味着相关数据不可用；一台电源控制器的过流则可能要求立即切断输出，必要时由独立硬件保护。用一个统一的错误码表或者软件队列，不能代替硬件安全设计。

## 1.1.7 设计怎样从需求里长出来

到现在为止，我们已经找到几个职责：采集测量、保存设备信息、接收用户操作、决定当前页面、绘制页面。但不要急着为每个职责建一个文件夹，更不要立即创造 `AbstractManagerFactory` 一类与问题规模不相称的框架。

先做一个最小设计就够了。应用模型保存温度及有效性、报警阈值等信息；应用控制器接收输入操作并维护当前页面与设置规则；界面渲染器读取这些信息，调用 SSD1306 的绘图能力。传感器服务把测量结果交给应用模型，而不是直接在屏幕上写数字。

一个足够小的结构可能是：

```text
app/
  app_model.h        # 设备数据和界面状态的基本定义
  app_controller.c   # 输入操作引发的状态改变
ui/
  screen_renderer.c  # 根据模型决定画什么
platform/
  fake_sensor.c      # PC 阶段产生模拟测量结果
```

这里只是帮助理解的候选布局。我们不会在 1.1 节就要求你建立这些文件，也没有规定这些职责必须永远使用四个文件实现。到了第二章，我们会用真正的 CMake 工程检验：接口到底需不需要再拆分，哪些数据不应暴露给其他模块。

假设产品经理突然说：“设置页允许编辑阈值，但只有按下确认键后才生效。”我们便需要区分一个尚未确认的编辑值，以及已经生效的设备设置。这个需求变化会影响设置交互和配置管理，却不应要求 SSD1306 驱动修改 I²C 命令。反过来，换一种字体或显示屏型号，可能影响渲染代码，却不该改变报警条件。

这就是我们判断模块边界的一种实用方法：**看看未来哪些需求会让它变化。因不同原因变化的职责，通常不宜长期挤在一起。** 这是启发式判断，不是要求一开始拆到最细。对于简单的小工具，适度合并模块可能更清楚。

## 1.1.8 把“能工作”变成“知道为什么能工作”

本书不会把“实验跑通了”当成唯一验收标准。我们还需要回答：哪些情况被测试过？哪些结论只是合理猜测？如果需求变化，读者能不能独立判断该改哪里？

对于今天的三页面仪表，最早的实验完全可以只在 PC 上进行。我们人为输入一条 25.6°C 的有效测量，观察监控页文字；触发一次“下一页”操作，检查当前页是否改变；再把传感器状态设为无效，检查界面是否显示离线，而不是照常宣称读数有效。

我们还可以故意构造错误。例如在 `SETTINGS` 页面编辑报警阈值时，向模型注入一条新温度。按我们的职责划分，编辑中的数字不应被新测量覆盖；界面仍应允许保存或取消设置。再比如把当前页切换十次，查看设备阈值是否被意外重置。这些实验暂时不需要逻辑分析仪，但能帮助我们在接真实硬件前发现应用规则中的错误。

把这种检查写成表格，会让后续实现更有方向：

| 操作或异常 | 应当观察到的行为 | 不应发生的行为 |
|---|---|---|
| 新有效温度到来 | 当前测量值更新 | 当前页被重置 |
| 用户切换页面 | 显示切到目标页 | 报警阈值被改变 |
| 传感器失联 | 数值被标记无效、界面仍能操作 | 永远等待读数或继续冒充实时值 |
| 设置页取消编辑 | 保留已生效阈值 | 未确认值被写入正式配置 |

本节这些都是**待实现、待验证的行为要求**，不是声称已经在 ESP32 实机测得的结果。下一节会将它们进一步写成带编号的需求与测试方案；之后的章节才逐步完成代码和真实硬件验证。

## 1.1.9 动手之前，先做一次设计判断

请给自己几分钟，不要看代码，完成下面这个小练习。

**题目：** 三页面仪表新增一种功能：在 `MONITOR` 页面长按按键两秒，将温度显示单位从摄氏度切换成华氏度。历史数据仍要保存原始测量值，重新启动后保留用户选择的显示单位。

先回答三个问题。第一，按键识别模块应该上报什么样的操作，是否需要知道“摄氏度”和“华氏度”？第二，测量模块内部应该保存摄氏度、华氏度还是两份数值？第三，如果以后 OLED 换成 LVGL，这项功能最理想的情况下需要修改哪些部分？

可以先画一个只有三四个框的草图。不要因为还不会画标准 UML 就停止，也不用急着定义一整套事件总线。只要把**谁拥有哪份信息、谁处理什么请求**画出来，就已经迈出重要一步。

**自查提示（不直接给完整架构）：** 按键的物理持续时间属于输入识别问题，单位偏好属于设备配置，单位换算属于数据呈现或明确的格式化策略。试着让任何一个模块都不必同时知道这三件事。想一想：如果为了实现单位切换，你必须修改 `ssd1306_send_command()`，是不是说明某个职责放错了位置？

如果你能讲清楚上述推理，就已经开始从“调用显示库”走向“组织显示产品”。即使还没有写一行新代码，这种判断依然会影响后面软件能否长期维护。

## 1.1.10 回到开头：我们到底完成了什么？

开头那块只会显示 `25.6 C` 的 SSD1306 并没有错。它证明了屏幕与程序的一段路径能够工作。但它没有告诉我们：页面由谁管理、采集失败怎样传播、数据是否新鲜、设置如何确认、用户操作应当影响哪份状态。

这节课做的事情，是把这些被“显示成功”掩盖的问题重新摆到桌面上。我们没有急着选任务数量，也没有先制定一套看起来很完整的类图，而是从使用者能够观察到的行为，逐渐分辨数据、职责和技术选择。

下一节 **1.2《让产品构想变成可以验收的需求》** 会沿用这个仪表，把“更新要及时”“掉线还可操作”“历史要保存”等模糊描述，转化成带条件、边界与测试方法的需求。之后，我们才有足够的依据决定模块接口、程序结构与执行方式。

**本节检查点**：如果有人现在提出“再加一个 Wi-Fi 页面”，你不必立刻知道怎么编写 Wi-Fi 代码；但应该先询问它对用户有什么作用、会修改哪类状态、和现有页面如何交互、断网时应出现什么行为。能提出这些问题，就说明你已经开始用产品工程的方法看待技术。
