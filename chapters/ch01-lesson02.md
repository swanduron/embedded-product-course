# 第 1 章 · 第 1.2 节：让产品构想变成可以验收的需求

> **阶段**：产品与软件基础 · **运行环境**：纸面 / PC · **硬件**：无 · **产出**：需求基线 `REQ-001`～`REQ-008`、测试计划与待决问题。以下数值均为**教学假设**，不是从真实用户调研得到的产品指标。

## 1. 本节解决什么问题

“做一个带三个页面的温湿度仪表”只是产品构想。它没有告诉开发者：什么时候更新？页面如何切换？断线之后保留旧值还是显示无效？重启后恢复哪个页面？

如果不回答，程序员往往会先写驱动，再把所有临时决定塞进 `main()`。我们要做的是把一句构想变为**可观察、可验证、可追踪**的行为需求，而不是直接选择 FreeRTOS、LVGL 或某个 OLED 库。

本节完成后，读者应能（1）区分需求和实现手段；（2）把模糊语句改写成可测试约束；（3）为每个需求提出至少一个正常测试和一个边界/故障测试；（4）指出尚未决定而不能擅自猜测的内容。

## 2. 产品情境与边界

**用户故事**：桌面上的小仪表能让使用者查看当前温度和湿度、查看最近一段时间的温度走势，并用旋钮设置高温报警阈值。传感器不可用时，设备仍允许操作页面，不能把失效数据装成真实数据。

**本阶段范围**：三页 UI 的行为定义、模拟测量值、报警阈值调整、离线显示、重启配置恢复的期望行为。

**本阶段不做**：真实 I²C、SSD1306 刷新、非易失存储实现、实时性证明、RTOS、生产级安全认证。这些会在对应后续章节实现并验证。

### 三个页面的职责

- **Monitor**：显示最新有效温湿度、采样时间/新鲜度和报警/离线状态。
- **History**：显示固定长度的温度历史；尚无数据时展示“无历史记录”，不伪造曲线。
- **Settings**：编辑温度报警阈值，可确认或取消，保存结果供后续重启恢复。

**设备状态 ≠ 页面状态**。传感器在线、阈值数值属于设备模型；当前页、编辑焦点属于 UI 状态。切页不应抹掉设备数据。

## 3. 将“不错的体验”变成需求基线

以下时间和阈值只是首轮可调整的**示例验收目标**。它们首先用于软件模拟器和单元测试，真实硬件性能需在后续章节另行测量。

| 编号 | 需求（可观察行为） | 初步验收证据 |
|---|---|---|
| REQ-001 | 用户可在 Monitor、History、Settings 三页循环切换，切页不改变测量数据和报警阈值 | 连续切页 12 次，顺序正确，数值不被重置 |
| REQ-002 | 有效测量数据到来后，Monitor 最迟在 1 秒内显示新值（PC 仿真目标） | 注入新样本并检查视图在时限内更新 |
| REQ-003 | 当样本连续 3 秒没有更新，显示数据过期；明确显示无效/离线，不把旧读数当当前值 | 停止样本输入，推进模拟时钟超过 3 秒 |
| REQ-004 | 传感器离线时，页面操作依然可用，模拟输入到可见切页的延迟不超过 200ms | 注入断线并连续触发切页，记录响应时间 |
| REQ-005 | 温度历史最多保存最近 60 个有效采样点，容量满时丢弃最旧点 | 注入 61 个有效样本，验证长度与顺序 |
| REQ-006 | 阈值可在 0.0～50.0°C 范围内以 0.5°C 步长编辑；取消不生效，确认才更新设备设置 | 测试边界值、取消、确认和非法输入 |
| REQ-007 | 温度达到或超过当前阈值时产生高温报警；无效测量不得被判作正常温度 | 注入阈值上下边界及无效样本 |
| REQ-008 | 重启后读取最近一次成功提交的阈值；损坏的配置不能无条件应用 | 使用模拟存储测试正常重启与损坏配置 |

**注意**：REQ-003 的“过期”与“传感器被检测为离线”在真实系统中可能不是同一个诊断结果。本阶段 UI 可以统一显示“数据不可用”，后续故障管理章节再细分故障码。

## 4. 学会区分需求、设计和实现

“应该每 100ms 调用 `lv_label_set_text()`”并不是产品需求，而是某种实现细节。真正的需求是“新数据在规定时间内可见”。

- **需求**：离线时仍能切换页面。
- **设计约束**：传感器访问不能无限阻塞 UI 处理。
- **候选实现 A**：非阻塞轮询 + 有限超时。
- **候选实现 B**：采集任务与 UI 任务分离，通过状态快照/事件传递结果。
- **选择依据**：目标平台、最大响应延迟、复杂度、可验证性。尚无足够数据时不直接指定 RTOS。

这种区分让未来从 SSD1306 换成 LVGL，或从 ESP32 换成 RP2040 时，需求 ID 不需要随着 API 更换。

## 5. 一份最小的数据契约（概念性代码）

本节不要求编译这段代码；下一章会将其放入真正的 C 工程并配套自动化测试。

```c
/* 本节只讨论数据边界，尚非完整可编译工程。 */
typedef struct {
    float temperature_c;
    float humidity_pct;
    unsigned long sample_time_ms;
    bool valid;
} measurement_t;

typedef struct {
    float alarm_threshold_c;
    bool high_temp_alarm;
} device_settings_t;

typedef enum {
    PAGE_MONITOR, PAGE_HISTORY, PAGE_SETTINGS
} page_id_t;
```

`measurement_t` 不应该包含 SSD1306 像素坐标；`device_settings_t` 不应该包含 GPIO 编号；`page_id_t` 不应该决定 SHT31 如何发 I²C 命令。

## 6. 故障实验：让“没数据”与“零度”不能混淆

在 PC 模拟器中模拟以下序列：

1. `t=0ms` 收到 `temperature=25.0°C, valid=true` 的样本。
2. `t=1000ms` 停止采样输入，仍可切页。
3. `t=3100ms` 根据 REQ-003 标记数据过期；不要显示 `0.0°C`，也不要把旧值当作实时有效读数。
4. `t=3200ms` 用户进入 Settings 并修改阈值，UI 仍能响应。
5. `t=4000ms` 注入新有效样本，数据恢复有效，历史记录继续更新。

边界测试要关注 `t=3000ms` 和 `t=3001ms` 的行为；本节规定的过期条件为 `now_ms - last_sample_ms > 3000`。后续使用单调时钟和适当的无符号时间差实现，以避免时间回绕问题。

**工程限制**：当前 HTML 交互演示只能展示失联状态和切页，不是 1 秒刷新或 200ms 响应的精密测量工具。量化验收必须由后续测试程序实现。
