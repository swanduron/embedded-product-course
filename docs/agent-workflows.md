# 交给 Codex 的教材写作、辅导与审稿工作流

本说明为任务入口；以 `AGENTS.md`、`governance/` 和 `decisions/` 的现行文件为准。课程负责人当前的 Git 工作目录为 `~/Documents/project/embedded-product-course`，实际执行前应以 Codex 已打开的路径为准。

## 用法 A：继续编写教材

> 请打开本地 `embedded-product-course` 仓库，先阅读根目录 `AGENTS.md`，按照“写作模式”读取课程愿景、四层语义模型、14 章总纲、已确认决策、教学假设、写作规范，以及本次章节的前置正文。先检查 `git status`，保护未提交的修改。
>
> 本次任务是继续编写【指定章节/小节】。请先用一段话确定本节要解决的**产品问题、现有方案的限制和学习者的知识断层**，再写连贯教材正文。需要有真实情境、逐步推导、适量技术细节、可复现或纸面验证、独立迁移任务。避免按“产品需求/原理/实现/测试”逐项填成 AI 风格提纲，也不要将 OLED/RTOS/LVGL 清单误作教材主线。
>
> 以 Markdown 为正文源；若本节要发布到 HTML，检查 `scripts/build_site.py` 当前只包含 1.1 与 1.2，按需要增加新章节的自动生成和导航，并验证生成结果。不要自行冻结假设、改变 14 章结构、commit 或 push。最后给出修改清单、实际测试、待确认事项。

## 用法 B：作为我的学习导师

> 我正在学习《现代嵌入式产品工程》的第【章】第【节】，目前具体问题是【我的问题/代码/实验现象】。请先按仓库 `AGENTS.md` 的学习辅导模式阅读该节、前置内容与已有实验。以产品实际需求解释为什么遇到这个问题，再逐步说明原理、状态/数据流、实现接口和故障边界。
>
> 不要默认我已经掌握“讲过”的内容，也不要只给库 API 或空泛鼓励。请先直接回答当前问题，再用适量的例子、可复现验证和一个可迁移的小任务帮助我独立做出来。如果是教材写得不清楚，请指出具体章节位置并提出修改建议；不要未经要求修改正式文件、自动记录我已掌握或替我批准章节。

## 用法 C：独立审稿

> 请实际阅读指定章节及治理规范，以“教材主线、贯穿产品、案例和技术选项”四层区分为前提，对正文进行独立审查。检查读者不依赖表格和图片能否读懂推理、知识先修是否完整、技术是否有需求来源、设计是否比较取舍、案例是否能迁移、代码和测试声称是否有证据。输出“符合 / 需改写 / 缺验证证据”，逐项定位到文件和段落并给具体建议。未经明确要求先不要修改源码或宣布正式审核通过。

## 每次工作的简短回执

- 读取的仓库基线及所依据的决策
- 本次新增的产品能力或教学能力
- 真实修改的文件与原因
- 实际运行的构建/检查命令和结果
- 未测试、不确定或仍须批准的事项
- 适合学习者继续完成的一小步

日常答疑无需输出长篇治理报告；需要审核时才完整展示证据。

## 本次更新包的导入

先在原 Git 工作目录运行 `git status`，保存尚未提交的工作，再把更新包内的 `embedded-product-course/` **合并到现有目录**。更新包不含 `.git/`，不要覆盖 Git 历史。检查 `git diff` 和 `git status --short`，重建 HTML，按课程负责人的决定提交并推送。
