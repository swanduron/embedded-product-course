# 教材叙事与写作规范 v1.3

> 适用于《现代嵌入式产品工程》的全部正文、实验引导、例题、案例分析和审稿。它约束的是**读者怎样学会**，不是文档目录怎样排版。自 v1.2 起，章节作者必须阅读本规范。

## 1. 这本书应该是什么阅读体验

本书是一部可连续阅读、可动手实践、可返回复习的**工程教材**，而不是会议纪要、培训 PPT 的讲稿、API 速查表，或聊天助手的回答汇总。读者可以没有上过一门完整的 RTOS 课程，也不应被突然出现的术语和代码击退；与此同时，教材必须保持专业准确，不因浅显而牺牲因果关系和限制条件。

每节应让读者沿着一条连续的工程问题走下去：看到实际情境中的困难 → 发现此前方法的边界 → 追问原因 → 推导设计选择 → 落地实现或明确当前尚不实现的部分 → 使用可复现证据检验 → 在新条件下再次使用。**这是思考路径，不是八个必须逐行出现的标题。**

## 2. 正文必须是“讲透”，不能只列出“讲什么”

- 主要概念采用连贯的解释性段落展开。每个重要结论都说明它从哪一个具体问题得出，必要时给出反例、运行结果或局部代码。避免用“需求、设计、实现、验证”四个名词代替完整的推理。
- 对刚出现的新术语，先通过读者熟悉的情境建立含义，再命名术语，随后给出精确定义。例如先看到“读数可能早已过期”，再引入 `valid` 和数据新鲜度；不要先堆数据结构名词。
- 文章需有清楚的段落衔接：上一段提出的问题，下一段要回答；图表与代码必须被正文引用、解释其意义。禁止把十张表并排放着而不推导。
- 保留必要的技术密度：状态变化、数据流、时间尺度、执行上下文、错误传播、界面生命周期、资源边界等，不能因“像故事”就省去关键机制。
- 表格适用于对比、规格、测试矩阵，列表适用于步骤或核对，不应用作整节正文的主体。粗略判断：如果隐藏所有表格和列表后只剩几句口号，此节不合格。
- 以完整案例为核心，比堆五个小故事更好。同一个案例至少经历初始成功、需求变化、失败场景与改进，并持续引用具体角色和数据。

## 3. 语气与文风

采用理性、沉稳、有耐心的教材口吻，用“我们”引导推演是可以的，但不要像聊天机器人反复称赞读者、宣布“关键洞察”或兜售某种万能架构。尤其避免：

- 空泛赞美：“这个问题太棒了”“这绝对是最重要的思想”；
- 套话堆叠：“本质上、实际上、真正、核心、赋能、颠覆、工业级”连续使用；
- 机械对仗：“不是 A，而是 B”在每个段落重复出现；
- 未经论证的绝对化：“真正的项目肯定不使用 while(1)”“工业级必须有 RTOS”；
- 口号式小标题、结尾连续反问、逐段一句话的碎片式排版；
- 把完整的推导跳过，直接列“架构建议 / 十个注意事项”。

不要为了亲切而故意简单化，也不要把学习者过去失败的经历写成对个人能力的定性。文字应能够脱离对话记录独立阅读。

## 4. 如何安排示例与代码

一个好例子要包含**背景、输入或约束、可观察结果、推理与局限**。同一份代码至少解释关键的执行路径以及为什么放在该模块，而不是写“下面代码很好地实现了功能”。代码出现必须标明其证据等级：伪代码、独立可编译代码、通过 PC 测试、实际硬件验证；不得把片段当完整工程。尽量遵循“读者先预测行为 → 运行/推演 → 解释结果 → 修改需求”的顺序。

在解释 `ssd1306_draw_string`、`lv_label_set_text` 等 API 时，关注它们在系统中的职责边界以及不承担的行为。先做一个朴素实现，让真实的扩展需求暴露问题，再引入新的模块/抽象；不提前堆框架。引用代码时给出文件名、调用方、数据所有者、错误路径和测试方法（当前章节不涉及的部分可明确留待后续）。

## 5. 教学节奏与篇幅

篇幅由概念难度和实例深度决定，不以字数替代质量。对第 1 章这类建立思维模型的正式正文，首次成稿一般应能支撑**完整的 15–25 分钟阅读与思考**；只有几百字、几张表的内容应标为“课堂提纲”，不能作为正式教材正文。对操作型章节，正文可以较短，但必须有完整的操作环境、实验可复现步骤、观察与解释。必要时分成 1.1a/1.1b 等小节，避免又长又散。

- 一节课集中解决一个核心问题；可有两三个自然衍生的问题，不抢教尚未出现的整章知识。
- 读者遇到知识悬崖时，增加“桥接解释”与最小模型，不以加更多参考链接代替教学。
- 允许适度重复同一概念，但每次必须增加新的约束、场景或深度，不能复述口号。
- 初学者可能卡住的地方要写出思考过程：怎么识别错误想法、为什么看起来合理、什么证据能够推翻它。

## 6. 练习与答案如何设计

练习必须服务于学会，而非制造考试压力。至少有一处“先想一想”的暂停点和一项迁移练习，前者可以提供启发提示，后者不立刻给全套答案。可给出**答案分析**作为自查，解释错误选项的诱惑及错在哪里。提供清晰的验收条件，让读者知道是需求描述不完整、模块职责混乱，还是实际代码有 bug。

不需要每节堆五种选择题。优先选择要求读者做出工程判断的练习，如把模糊要求写成可检验的行为、明确状态所有者、设计一个故障实验，或替换产品约束后修改架构。

## 7. Markdown 与 HTML 的一致性

Markdown/源码是**内容权威**；HTML 是读者端。图、交互、提示、代码折叠等可以强化教学，但不能取代解释性文字。即使不运行 JS、打印成 PDF 或只看 Markdown，读者也应能完整理解主要论证。交互实验必须写清楚它演示什么、不能证明什么；当交互不可用时应有文字替代说明。

正式发布前：用 Markdown 渲染 HTML，并人工检查阅读流、标题层级、代码/表格宽度、公式、图示说明和交互工作情况；禁止仅根据字符长度或测试通过率判定教材可读。

## 8. 审稿时的五个问题

1. 读者能否用一句话说出这一节出现的**真实工程困难**？
2. 每个新的概念、模块或技术选择，是否都能回指到前文某个需求或失败？
3. 去掉表格与要点后，正文是否依然形成**连续完整的论证**？
4. 是否存在“示例跑通了，但读者仍只会 include”的风险？是否安排了可迁移的独立动作？
5. 有没有只在聊天语境里才成立的省略、没有证据的夸大、或将示意图当成了验证结果？

审稿不通过，应给出具体段落与改写建议，而不是简单要求“写得更丰富”。

## 9. 两种写法的对照

**不能作为教材正文的提纲：**

> 设备要三页 UI。需要页面管理、数据模型、按钮事件。设计模块接口并验证。

**更接近教材的写法：**

> 让 OLED 显示温度以后，我们往往会在主循环中把新数值写到固定坐标。第二天要增加“设置页”，问题突然发生了变化：按键已经不只是让显示内容改变，还必须决定当前操作指向哪个页面。若把这一判断写进 SSD1306 驱动，它就需要知道产品一共有几页、按钮有什么意义，甚至必须知道温度报警阈值如何保存。这样一来，原本只需负责像素传输的驱动开始承担产品行为。我们先不写代码，而是问一个更小的问题：**当前页面究竟是谁的状态？** 只要回答清楚这一点，文件和接口的划分就有了依据。

示例只说明“展开推导”的方法；正式正文还需要配合具体验证、可能的取舍和学习练习。

## 10. 写作工作法：先写完整推导，再添加阅读组件

后续每一节实行两轮写作，而不是“先填模板，填完即提交”。第一轮只写读者能连续读下去的**教材正文**。作者要亲自走过案例从初始可行到新增需求再到失败与设计改进的过程，回答为何需要这项技术、它代替了哪一种旧做法、带来了哪些新约束。第二轮再加入插图、代码、测试表、思考题与边栏。最终审稿应把正文独立抽出来阅读，检查其是否依然成立。

写作前先记录本节的“读者起点”和“最终能力”之间的差距。例如读者会调用 `ssd1306_draw_string()`，却不理解页面状态与数据模型。正文必须**亲自陪读者跨过这一段差距**，不能以一张分层图或者一句“应用层和驱动解耦”代替解释。

禁止用每一段都由标题、三条 bullet 和一句口号组成的方式模拟教材厚度。允许使用列表作为检查、任务或规格，但每张表之前应交代为什么需要表、之后应解释读者能从中得出什么判断。交互组件用于让读者检验理解，而不是用动画掩盖薄弱论证。

## 11. 常见的“AI 味”及修订方法

- **口号多，因果少**：写“产品需求驱动架构”之前，先展示哪个新增需求让现有代码具体失败，哪个职责因此必须搬走。
- **同义句重复**：连续说“不是只会调用 API”“真正重要的是架构”“系统思维更重要”不构成新知识。每次重申必须增加一种新约束或实际例子。
- **名词先行**：不能在读者不知道问题时先投放 HAL、事件总线、领域模型、依赖注入；先描述一个失败或边界，再介绍恰好能解决它的概念。
- **假装确定性**：不使用“工业上一定”“唯一正确的结构”等断言。应说明适用条件、最小方案、何时需要升级以及仍未验证的部分。
- **练习形同装饰**：不能只让学生选择显而易见的选项。至少有一题让读者面对变化的需求，独立划定数据所有者、接口与测试。
- **把学习者当成被鼓励对象**：少用“你已经非常棒了”等肯定式话术；改用具体可观察的进步标准与错误原因，保留学习者的独立判断。

## 12. “正文可读性审查”的实际门槛

章节作者提交时，必须附上一份最多一页的编辑说明，说明：（1）案例最初遇到的真实阻碍；（2）本节如何让读者亲眼看到旧办法不够；（3）哪一段完成原理到设计的推导；（4）至少一处读者容易误解却在正文里得到澄清的地方；（5）独立迁移练习的验收规则。审稿人不仅核对是否出现这些词，还必须定位到具体段落。

对建立概念的章节，至少通过一次**连续阅读检查**：不看表格、配图和代码，仅阅读正文段落，仍然能说明问题、推理、结论与局限。对代码主导章节，至少通过一次**执行路径检查**：从输入到输出能跟踪数据与错误如何流动，不用依赖未提供的隐含工程。

发现读者“只会 include、能照抄不会改”的反馈时，优先考虑增加推导、边界情景和独立迁移任务，而不是盲目增加解释 API 的篇幅。所有反馈记入 `feedback-and-progress.md` 规定的流程，更新应当能追溯到具体教学问题。
