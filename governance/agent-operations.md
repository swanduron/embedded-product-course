# 多 Agent 运行规程与上下文加载 v1.2

## 唯一权威与层级
正式发布的仓库文件为唯一课程事实来源：`vision.md`（价值与原则） > `curriculum.md`（结构与目标） > `decisions.md` 及 ADR（已批准决策） > 已审核章节/接口契约 > 具体实验源码。聊天及 AI 记忆只是讨论输入，不可替代已发布基线。若存在冲突，停止擅改并产生疑问/提案。

## 新 Agent 启动时的必读顺序
1. `README.md`：版本、目录及当前发布状态。
2. `governance/vision.md`、`learning-contract.md`、`editorial-style.md`、`curriculum.md`。
3. `governance/agent-operations.md`、`decisions.md`、`release-policy.md`。
4. 所属章节、上一阶段依赖和 `cases/` 相关案例（如存在）。
5. 实验目录的 README、构建版本、验证记录（如存在）。
6. 学习/硬件反馈（仅与当前任务相关的部分）。
Agent 必须在工作摘要中列出读取的基线版本和缺失文件，不应声称读过未提供的资料。

## 职责和允许的修改
- 课程讨论/架构 Agent：分析提议、更新待审提案，不直接变更发布基线。
- 章节写作 Agent：只改被分配的章节草稿、图示、必要实验；跨章改动必须发 CCP。
- 实验工程 Agent：实现、构建、测试；返回命令、环境、失败/通过证据，不擅改产品需求。
- 答疑 Agent：以当期章节为准解释疑问，记录真实困难和可能的教材缺陷，不代替验收。
- 审核 Agent：检查技术正确性、教学难度、跨章节契约、版本和验证证据，可拒绝发布。
- 维护/集成 Agent：仅依据批准变更更新索引、构建 HTML、生成包和发布记录。
角色可以由同一 Agent 承担，但不能绕过审查门槛。

## 每项任务的输入契约
指定：任务 ID、章节/路径、基线版本、产品需求 ID、已有接口/测试、允许修改路径、产物清单、完成定义。如缺少关键输入，先查现有文件；仍缺失则记录假设，不把假设当既定结论。

## 每项任务的输出契约
输出：更改路径、实现的需求 ID、采用/放弃的方案、依赖变更、执行过的命令和结果、未验证部分、引入的风险、建议 CCP、是否具备发布条件。禁止只说“已完成”而无文件/证据。

## 防止上下文漂移
- 不能根据聊天摘要改写已冻结的 14 章结构；需要 CCP。
- 新增例子要标明主线/延伸/选修，防止课程无限膨胀。
- 不把 SSD1306 命令式绘图和 LVGL 对象模型混为一个接口。
- API 版本不明、管脚分配未冻结、硬件未打样时必须显式标记。
- 不因为代码由 AI 生成就放松构建和测试要求。

## 审核与合并
完成草稿 → **独立正文连续阅读审查（详见 editorial-style.md）** → 检查契约、术语、先修 → 实验构建/测试 → 教学审查 → 人工批准 → 更新内容源 → 生成 HTML → 检查链接与交互 → 标记发布。任何一项失败则保留 draft，不宣称已发布。
