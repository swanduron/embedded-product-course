# 章节写作工作模板 v1.3（给作者，不是给读者打印的空白提纲）

**重要**：以下是写作检查顺序，不应一项一项机械复制为正文小标题。正文应依据 `editorial-style.md` 写成连贯教材。

## 作者开工前填写（不放进正式正文）

- 章节 / 基线版本 / 状态（draft、reviewed、verified）：
- 读者已学会、只听过、尚未接触的前置概念：
- 本节唯一的核心工程问题：
- 该问题在长期项目中的直接后果：
- 从哪一处旧实现的限制引出本节：
- 预计出现的两三个理解障碍：
- 本节与后续章节的接口约定及测试依赖：

## 正文组织建议

用实际产品情境作为开端，描述需求发生变化时旧方案暴露的具体不足；在关键分歧处逐步推理（可以插入极短代码、时序图或对比）；最后得出**有限度的设计结论**并说明何时不适用。适时加入“先预测”暂停点，给读者独立处理一个改动过的相近需求。

如果章节需要代码：先呈现最简单可理解的机制，再展示工程实现与其测试；如果本章只讨论需求定义，不要为了凑固定标题强行引入没有必要的代码。

## 作者交付附录（可以结构化）

- 需求与测试编号：
- 术语和接口复用情况：
- 示例/源码及证据等级：
- 故障和边界测试：
- 独立练习的验收规则：
- 未验证事实与开放问题：
- 对课程总体结构的变更提案：

## 发布前编校记录

- [ ] 内容能脱离聊天记录独立阅读；主体不是罗列要点
- [ ] 已按 editorial-style.md 完成连续阅读与执行路径审查
- [ ] 提交了简短编辑说明并定位到正文证据
- [ ] 图表和代码都有解释，例子有结果与局限
- [ ] 没有未经介绍的术语跳跃
- [ ] 没有反复使用“不是 A 而是 B”等模板化表达
- [ ] 存在具体的设计推导，而非只宣布最佳方案
- [ ] 有练习、有答案分析或可自查标准
- [ ] Markdown 和 HTML 的章节正文同步
- [ ] 技术事实、示意、真实测试证据的层级标记清楚
