# 教材四层语义模型：主线、产品、案例和技术

> 作用：避免新 Agent 把技术清单误当成教材主线。本文解释 `vision.md` 的定位，不代替 `curriculum.md` 或已批准决策。治理修订待课程负责人审核。

## 四个不能混同的层次

| 层次 | 含义 | 本教材中的例子 |
|---|---|---|
| **教材主线** | 从构想到可交付产品的工程过程，包含使用情境、需求、架构、取舍、实现、验证、产品化与交付 | 一个产品要求怎样转化成可验证行为与可靠工程 |
| **贯穿产品** | 跨章节持续演进的产品载体 | 室内桌面环境监测终端（具体用户群仍为教学假设） |
| **阶段案例与能力** | 为解决产品中的特定困难而引出的练习，必须在后续阶段复用 | 三页面 OLED、按键消抖、统一故障管理、同地址双屏与总线竞争、任务通信、产测 |
| **支撑技术** | 解决问题的候选工具，而非课程目的 | C/CMake、SSD1306、ESP32、RP2040、FreeRTOS、LVGL |

严禁将以上四者统称为“教材技术主线”。回答“这本书在教什么”时，应先解释完整产品工程过程，再介绍贯穿产品及选用的技术。

## 贯穿产品的使用逻辑

桌面环境监测终端用于练习从模糊构想到真实可验证的产品。当前候选使用场景是家庭、办公室或个人工作台上的室内环境观察；当前状态、历史趋势、异常提示和参数设置是产品功能方向。**这些是工作假设，不是用户调研完成或商业市场已验证的事实。**

Monitor、History、Settings 三页，是从“看当前状态、看历史、改参数”三类用户任务推导出的候选交互方案。应讨论一页/两页/三页等选择的代价；不得为已有 SSD1306 驱动倒推产品必然需要三页。SSD1306 显示字符是局部驱动验证，不是完整产品完成。

可换 ESP32/RP2040 核心板用于教学和产品构想验证。丰富的实验底板不是最终专用产品必须照搬的 BOM。工程样机与小批量验证应练习删减外设、制造、产测、版本、维护和成本取舍。

## 用一个需求串起多个章节

设想“传感器失联时，用户依然能切换页面”。先定义用户应观察到什么：读数明确无效、页面仍响应。然后给出可测量的时间边界（例如第 1.2 节使用的 **200 ms 教学假设**），再比较有界非阻塞循环与独立任务。接着在 PC 用模拟时钟与假传感器复现问题；在真实 MCU 上验证总线超时、输入与显示延迟；在 RTOS 章节研究并发通信；最后以故障注入和产测确认产品行为。

因此，技术选择必须从产品行为推导，不能“因为本章讲 FreeRTOS，所以造一个需求来证明必须用任务”。

## 章节作者的六个检查问题

1. 本节解决哪个用户任务或真实工程风险？尚有哪些工作假设？
2. 原有方案在哪个具体条件下开始失败？读者能看到怎样的失败？
3. 还有哪些可行方案？为什么当前约束下选择这个方案，什么时候反而不适用？
4. 新增或修改了哪些状态、职责、接口和工程资产？
5. 使用何种测试证据验证了什么？**尚不能证明什么**？
6. 下一节怎样复用今天的成果，而不是抛弃旧工程重头写？

这是作者的工作检查，不应被复制成六个机械的正文标题。正文必须通过 `editorial-style.md` 的连续阅读审查。

## 典型反例

- `ssd1306_draw_string()` 成功：只能证明特定绘图与传输路径，不能证明页面状态或配置保存。
- `xQueueSend()` 成功：证明 API 能调用，不证明必须采用多任务或已经处理资源竞争。
- LVGL 控件漂亮：不能证明数据所有权、传感器失联、报警和长期可靠性。
- 一块 PCB 能开机：不等于多台装配一致、持续运行或合规认证通过。
